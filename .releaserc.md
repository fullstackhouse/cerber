# Why the release config looks like this

`.releaserc.json` is JSON and cannot hold a comment, so the decision in it that
will look like an omission lives here — along with what guards that decision,
and what to do when a release stops half-way.

## There is no `@semantic-release/git`, on purpose

That plugin commits the bumped `package.json` and pushes it to `main`. The
ruleset on `main` requires a pull request, so that push is rejected —
`GH013: Repository rule violations found for refs/heads/main` — and the whole
release fails in `prepare`, before anything is published. It is how v0.35.0
came not to ship.

It cannot be fixed with a permission. `GITHUB_TOKEN` is not eligible to bypass
the ruleset: GitHub Actions is not an installable app, and the rulesets API
refuses it as a bypass actor outright (`Actor GitHub Actions integration must be
part of the ruleset source or owner organization`). Excusing the release would
mean a GitHub App or a stored token that can push to `main` — a credential that
exists only to get around the rule that nothing reaches `main` without a pull
request.

So the release doesn't push a branch at all. It writes exactly two refs, and the
ruleset has no opinion about either: the tag, pushed as `git push --tags` with no
branch refspec, and a note under `refs/notes/semantic-release-*` recording the
release channel (`pushNotes`, both in `semantic-release/lib/git.js`). The GitHub
release is an API call and the npm publish an OIDC exchange. The job's own
`GITHUB_TOKEN` covers all of it, and the rule holds for everyone including the
robot.

If you ever add a ruleset targeting tags or `refs/notes/*`, those two pushes are
what it will stop — the release writes nothing else.

## What that costs, and why it is cheap

`package.json` in git says `0.0.0-development` and stays there. The version is
real wherever it matters: `@semantic-release/npm` bumps the manifest before
publishing, so the published package — and `cerber --version` for anyone who
installed it — reports the true version. Only a build from a clone reads the
sentinel, and it is telling the truth when it does.

The alternative was leaving the last released number behind in the manifest,
which drifts: it would have said 0.34.0 for every release after it. A sentinel
cannot drift because it makes no claim. `git tag` is the record of what shipped.

## If you are tempted to add the plugin back

Releases will fail the same way on the next merge to `main`. Either keep the
version out of the committed manifest, or remove the pull-request rule from the
ruleset — but don't mint a credential whose only job is to get around it.

## What guards it

`src/release.test.ts` is what stops that reaching `main` unnoticed, because this
config is the one thing here that cannot fail on a pull request — it only runs
on the merge. It checks that this file is the config semantic-release actually
loads (`package.json` and a bare `.releaserc` both outrank it in cosmiconfig's
search order), that the file wires plugins only through `plugins` (a top-level
`prepare`/`publish` key or `extends` would otherwise load one past the list),
that the list is exactly `commit-analyzer`, `release-notes-generator`, `npm`
and `github` **in that order** — the recovery section below reasons from npm
publishing before the GitHub release — and that `version` is still the sentinel.

It also parses `.github/workflows/ci.yml`, because the config file is not the
only way to undo any of this. Parsing rather than grepping is deliberate: it
sees what Actions sees, so a `run: |` block, a `secrets['NAME']` lookup and a
flow-style `with: { token: … }` cannot hide in the formatting, and a comment
cannot trip it. Across the **whole** file it collects every secret named — by
`secrets.NAME`, `secrets['NAME']`, a dynamic `secrets[…]` lookup,
`toJSON(secrets)` or a job's `secrets: inherit`, case-insensitively, as Actions
resolves them — and requires the set to be exactly `GITHUB_TOKEN`. A PAT
anywhere in CI is a credential on this repo, and the release is the job that
could use it to push; not needing one is exactly what lets the release keep the
pull-request rule rather than bypass it. On the **release job** it then checks
that the checkout is handed no credential of its own — `persist-credentials:
false` is hardening and allowed, and omitting it keeps the job's own
`GITHUB_TOKEN`, which is the point; an explicit `true`, a `token:` or an
`ssh-key:` are not —
that `semantic-release` is invoked with no arguments — `--plugins` and
`--extends` override the config file entirely — and that the job's own
`concurrency` block is intact, read per job so moving it elsewhere does not
pass.

That credential scan has a negative control beside it, feeding each form to a
fixture, and the reason is worth keeping: its first version matched
`/secrets:\s*inherit/` against `JSON.stringify(workflow)`, where the text is
`"secrets":"inherit"`. It could never fire. A guard that cannot fail reads
exactly like one that works.

Two more guards sit outside the config. `scripts/refuse-sentinel-publish.mjs`
runs from `prepublishOnly` and refuses a hand publish of the sentinel; the test
runs it in both directions, because a guard that always exits 0 looks identical
from outside and this one stands in the release's own path. And the CLI's
`--version` is executed and compared against the manifest, rather than matched
in the source, since `const version = "0.5.0"` passed to `.version(version)`
satisfies any shape assertion while being the exact drift it guards against.

What none of it can see: a composite action, a reusable workflow, a change to
how `pnpm` resolves `semantic-release`, or a publish that goes around
`prepublishOnly` with `--ignore-scripts` or a pre-built tarball.

## If a release half-happens

The tag reaches the remote before anything is published (`tag`, `push`,
`pushNotes`, then the publish plugins — `semantic-release/index.js`), so a
failure after that point leaves a tag with nothing behind it. Everything below
follows from three facts; prefer re-deriving from them to following steps,
because this section has been wrong more than once by trying to enumerate
states instead.

**A published version can never be reused.** Deleting a tag whose version is
already on the registry turns a recoverable failure into one that cannot be
re-run at all. This is the only irreversible mistake available here.

**The refs and the registry are the evidence — not the log.** A run's
`Created tag vX.Y.Z` line is printed *after* the note push, so a run that died
between the two pushed a tag and logged nothing. Ask the remote and npm
instead; together they are complete:

```
git ls-remote --tags origin 'v*'            # what tags exist
npm view @fullstackhouse/cerber versions    # what actually shipped
gh release view vX.Y.Z                      # whether a shipped version has its release
```

Every remote `v*` tag above the newest published version is **stranded** —
there may be more than one, because a deterministic failure strands a tag per
merge. Nothing is stranded if no such tag exists, whatever the logs say.

**Releases are serialised, so another run may be holding the tags.** The next
one starts the moment the failed one ends, which is when you are reading this,
and its checkout holds the stranded tags locally — its `git push --tags` would
put back anything you delete. Before touching a ref:

```
gh run list --workflow CI --status in_progress --status queued
```

Cancel a queued run (safe — it has published nothing) or wait for an in-flight
one, then re-read the refs and the registry.

### Then there are only two actions

**A stranded tag** (on the remote, not on npm): delete it and its note, every
one of them, locally too — or the next `git push --tags` restores it.

```
git push origin :refs/tags/vX.Y.Z
git push origin :refs/notes/semantic-release-vX.Y.Z   # "remote ref does not exist" is fine
git tag -d vX.Y.Z
```

The note is often already absent, since `pushNotes` follows the tag push. Fix
whatever failed, then let the next merge release: it computes from the last
*published* tag, so it ships the stranded commits too, with complete notes,
most likely under the same number. A re-run of the failed run works only while
its commit is still the head of `main` — otherwise `isBranchUpToDate` finds the
checkout behind the remote and the job exits **green** having done nothing.

Leaving a stranded tag in place is the one thing to avoid: semantic-release
releases only what follows the newest tag, so the commits behind it become
unreleasable — a `feat:` stuck there ships as whatever the next merge's type
dictates, or not at all if the next merges are `chore:`/`docs:`.

**A published version with no GitHub release**: delete nothing, re-run nothing.

```
gh release create vX.Y.Z --verify-tag --generate-notes
```

Add `--latest=false` if a newer version has since shipped. Those are GitHub's
notes rather than semantic-release's, and the success comments on PRs and
issues are skipped; both are cosmetic, and the release itself is complete.

A red run whose version is on npm *with* its release has already finished the
job. Leave it.
